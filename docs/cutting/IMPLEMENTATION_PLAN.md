# Cutting workspace — implementation plan

> **Status:** proposal for review, nothing implemented · **Written:** 2026-10-27 · **Design:**
> [ARCHITECTURE.md](ARCHITECTURE.md)

This page lists the tasks for the cutting workspace in order. Each task is small enough for one agent session and
one PR, has acceptance criteria that a test can check, and keeps `cargo xtask ci` green. Task ids are `C<phase>.<n>`;
commits are `C2.3: per-object cut operation`, following `AGENTS.md`'s one-id-per-commit rule.

Every task also meets the standing criteria: no panics in shipped code (the clippy lints), wasm still builds,
`cargo xtask layers` passes, any new `cutting.*` command passes `engine/tests/command_sweep.rs`, and every new
command has a params doc and tests.

## Milestone: Cutting Workspace Prototype 0.1

These requirements come from the plan's §4 initial acceptance criteria. No hardware is needed.

| Criterion | Tasks |
|---|---|
| Builds and runs without breaking existing editor features | all (CI gate) |
| Opens an SVG with known physical dimensions | C2.1 (existing importer; test pins it) |
| Shows a cutting mat with accurate millimetre coordinates | C2.4, C2.5 |
| Assigns Cut / No Cut to individual objects | C2.3, C2.6 |
| Generates a cutting job from the document | C3.1–C3.5 |
| Shows the toolpaths and their execution order in a preview | C3.6, C3.7 |
| Saves and reopens with cutting settings intact | C2.2, C2.3 |
| Cutting operations go through the command architecture | C2.2, C2.3, C3.5 (all are `cutting.*` commands) |

## Phase 7 — Cutting UI

Owner, 2026-10-29: one long Cutting panel is hard to use. Its sections (Selection, Tool Settings, Print & Cut,
Job, Cutter) mix what is set once per document, what is set per object or layer and what is done for each cut.
Split them by job step: setting up stays in docked panels beside the art, like every other panel in the app, and
running a cut moves to a Send window of its own. All new UI is in new fork files under `crates/ui-egui`; the
upstream files change only at registration lines, added to ARCHITECTURE §7 as each task lands.

## Phase 15 — Templates made to size (idea)

Owner, 2026-11-01: an idea, not yet planned or sized. Sites such as [Templatemaker](https://www.templatemaker.nl/en/)
make papercraft and packaging templates to the size asked for: boxes (with a lid, tuck-end, gift, pillow, heart,
star), trays and inserts, envelopes and mailers, cylinders and cones, pyramids, prisms and the Platonic solids,
bags. A cutting app could make them in place: the net drawn as paths in the document, its lines already set to
cut or score, ready to print on, nest and send.

- **Clean-room.** Only the list of what kinds of templates exist comes from such sites. Every net is our own,
  worked out from its geometry (a box's panels from its inside sizes, a cone's from its radii and slant, a
  polyhedron's from its faces), never traced from or compared against another tool's output; its licence terms
  aren't known.
- **How it would fit.** One command per family (`cutting.template.box`, `….envelope`, `….cone`…) adding one
  group: the outline set to Cut, the folds to Score (or Perforate), the glue flaps marked; parameters in mm
  (inside or outside sizes, material thickness taken up at each fold, flap width and angle, lid clearance);
  remade in place with new settings as the puzzle is (C13.5); a Templates panel (C14.9: one for each feature) with a
  picture of the folded shape. Folds would show in the preview as score lines already do.
- **First candidates.** A tuck-end box, a box with a separate lid, a tray, an envelope, a pillow box, a
  cylinder and a cone (with a top diameter of 0 a true cone), a pyramid of n sides, the five Platonic solids.
- **To decide.** Which families first; whether the folds go in a layer of their own; whether a template can wrap
  the selected art (a box sized to it).

## How agents should work on this

- One task per branch (`cutting/C2.3-op-commands`) and per PR; the PR updates this file's status column (to be
  added once work starts) and ARCHITECTURE when a decision changes.
- Edit only the crates the task names; hook points in upstream files are single lines (ARCHITECTURE §7).
- Tests use hand-written inputs (small SVGs written from the SVG spec); never vendor sample files or files made
  with Silhouette Studio.
- Merge `upstream/main` into the fork's `main` at least weekly; resolve conflicts at the hooks first.
